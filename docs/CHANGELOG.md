# 改动总览（面试 / 简历用）

一句话版本：**把"能跑的命令行 NL2SQL 脚本"先做成"别人能跑起来的 Web 问数工具"，
再补上评估与可观测，最后加上「高价值用户运营台」把分析结果落到人身上 ——
形成「分析 → 决策 → 行动」闭环。全程没引入 React / ORM / 微服务 / 向量库，
新增依赖只有 pytest。**

## 第一阶段 · 让它跑得起来（P0）

| 改动 | 为什么 |
|---|---|
| 端口三处对齐为 8000（`app.py` 默认值原本是 8080） | 按 README 启动后打不开页面，是最容易劝退的一类问题 |
| 新增 `.env.example`（12 个变量 + 中文注释） | 没有模板时新人不知道要配什么、能配什么 |
| 删除命令行遗留版 `ai_sql_agent.py`（内含硬编码数据库密码） | 明文密钥 + 功能重复，留着只有风险 |
| 清理 README / 前端里指向不存在的 `web/` 目录的残留文案 | 文档路径与实际结构不一致，新人照着做会失败 |
| 新增 `sql/00_init.sql`：建表 DDL + 样例数据 | 没有建表脚本，项目"能看不能跑" |

## 第二阶段 · 安全边界（P1）

| 改动 | 为什么 |
|---|---|
| **修护栏漏洞**：`LIMIT 999999` 原本能绕过"没 LIMIT 才补"的逻辑，现在统一压到 `SQL_HARD_LIMIT` | 护栏的价值在于"无论如何都拦得住" |
| 支持 `LIMIT n` / `LIMIT n, m` / `LIMIT n OFFSET m`，按括号深度只处理最外层 LIMIT | 子查询的 LIMIT 属于语义，改了会改变结果 |
| 补充拦截 `LOAD_FILE` / `SLEEP` / `BENCHMARK` / `USER()` | 不是写操作，但能读服务器文件、拖垮数据库（由测试用例发现） |
| 新增 `logs/app.log` + `friendly_error()` / `error_for_model()` | 原始报错进日志，前端拿友好文案，模型只拿错误码 —— 错误脱敏 |
| README「安全」段写明"正则不是最终防线，生产要配只读账号" | 主动说清方案边界，比等别人问更专业 |

## 第三阶段 · AI 产品能力（P2）

| 改动 | 为什么 |
|---|---|
| **评估闭环**：`eval/cases.json`（25 条，含 3 条超纲）+ `eval/run_eval.py`（一键跑分） | 没有指标的 AI 功能无法迭代 |
| 判分用 `must_have` 关键词而非逐字比对 | 模型别名 / 大小写每次不同，逐字比对会把正确 SQL 判错 |
| 日志埋点：问题 / SQL / 重试次数 / 耗时 / 行数 / token(API usage) | 才能回答"这次改动让成本涨了多少、变慢了多少" |
| 提示词加入**低基数列取值采样**（`behavior_type → buy / cart / fav / pv`） | 模型不用猜枚举值，比反复强调"不要臆造"有效 |
| 多轮上下文带上**上一轮结果摘要** | 追问"再按类目拆一下"时模型才知道在拆什么 |
| **拒答通道**（`__无法回答__` → `refusal` 事件 → 前端友好提示） | 表里没有手机号却硬编 SQL，比报错更危险；拒答同时省掉后续调用成本 |
| 👍/👎 反馈落盘 `feedback.jsonl` | 最便宜的标注来源，为 bad case 分析埋点 |

## 第四阶段 · 整洁与可回归（P3）

| 改动 | 为什么 |
|---|---|
| 合并重复的 `load_dotenv` | 同一件事写在两个地方，改的时候必然漏一处 |
| `tests/test_guard.py`：30 个用例覆盖写操作拦截、`LIMIT` 各种写法、拒答识别、错误脱敏 | 护栏是关键路径，改提示词或改正则都必须能一键回归 |
| 前端会话存 `localStorage` + 「清空对话」 | 刷新不丢上下文 |
| `.gitignore` 补 `logs/`、`feedback.jsonl`、`user_tags.jsonl`、`.pytest_cache/` | 运行产物与私有配置不该进仓库 |
| README 补「产品思考」与 git 历史密码清理步骤 | 面试第一个问题是"有什么用、边界在哪"，答案该写在 README 里 |

## 第五阶段 · 从"问数工具"到"运营闭环"（本次）

| 改动 | 为什么 |
|---|---|
| `sql/00_init.sql`：维表补列（`users.member_level/city/register_at`、`products.item_name/category_id/price`、`categories.name`）并生成确定性样例值 | 维表只有 ID 时，"分层""客单价""推荐"全都没有数据支撑 —— 这三件事做不出来 |
| `GET /api/high-value-users`：**一条 SQL** 聚出 `buy_count / view_count / cart_count / category_count / last_active / tier` | 拉 50 个用户再逐个查就是 N+1；分层口径写死成常量（`TIER_CORE_MIN=20`、`TIER_GROW_MIN=5`）便于改口径 |
| `POST /api/tag-user` → `user_tags.jsonl` | "下发服务"要留痕，否则运营台只是又一块看板 |
| `GET /api/recommend`：候选 = 加购/收藏未购买（按加购降序）→ 不足 5 个用同偏好类目热销补齐；`reason` 由 LLM 写一句，**失败走规则兜底** | 推荐要能解释"为什么推给它"；接口不能因为模型抽风就 500 |
| `static/console.html`：概览数字 → 分层用户表 → 展开详情（画像 + 推荐商品 + 理由 + 下发服务） | 把"看完就走"变成"看完就能动手"，这是从工具到闭环的关键一步 |
| `static/index.html`：空状态垂直居中、加真实数据概览、示例问题分三组主题卡、间距/圆角/配色统一 | 首屏从"顶对齐 + 一片空白 + 一排 chip"变成有信息量、有层次的入口 |
| `#uid=xxx` 深链 | 可以把"某个高价值用户"的详情链接直接发给同事 |

## 明确没做的事（同样是设计决策）

- **没上 React / 构建工具**：两个页面都用单文件原生 JS，把"克隆即可运行"的摩擦降到最低；
  这个项目的 UI 复杂度（表单 + 卡片 + 表格）远没到需要框架的程度。
- **没上 ORM**：SQL 本身就是被生成、被展示、被审计的对象，ORM 只会把这条链路藏起来。
- **没上向量库 / RAG 框架**：表结构、列值采样、用户行为摘要直接拼进提示词就够用，
  这个数据规模下引入向量检索属于为了技术名词增加故障面。
- **没引入图表库**：给运营台加图表会带进一个外部依赖，而"分层 + 推荐 + 下发"这条动作链
  不需要图表也能说清；真要可视化，后端 `GROUP BY` 出数据后用 SVG 画更可控。
- **没写 `docker-compose.yml`**：本地评审机用的就是本地 MySQL，加一个跑不起来的编排文件
  只会增加"跑不通"的概率。
- **没上 `ragas` / `pandas` 做评估**：判分逻辑就是关键词包含 + 行数校验，标准库足够。
